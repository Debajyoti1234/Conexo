# P1.2B.9 — PLAN CHAT ARCHITECTURE AUDIT

> Audit-only phase. No code, migrations, RLS, storage, or seed changes were made.
> Scope: `supabase/migrations/*` + `lib/features/chat/**` + `lib/features/plans/**` + `lib/features/notifications/**` (read-only trace).

## Overall status

The Plan Chat feature is **schema-ready but functionally unwired**. The database already contains `conversations.type IN ('connection','plan')`, a nullable `conversations.plan_id` FK with `ON DELETE SET NULL`, and the `conversation_members` / `messages` tables required for group chat. However, **no client code path creates a plan conversation**, the inbox Plans tab renders only demo data, `PlanDetailsScreen` has no "Open group chat" action, and `findConversationForPlan` hard-returns `null`. A `temporary_chat_screen.dart` exists but is unreferenced dead code.

## 22. Required backend changes

### A. New RPC: `get_or_create_plan_conversation(p_plan_id uuid)`
- **Purpose**: Deterministically create (or return) a single `conversations` row per plan with `type='plan'` and `plan_id = p_plan_id`, and seed `conversation_members` from current `plan_members` where `status='joined'`.
- **Authorization**: Caller must be `creator` or have a `joined` `plan_members` row for the plan.
- **Idempotency**: Use `ON CONFLICT (plan_id) DO NOTHING` on a unique `conversations(plan_id)` constraint, or upsert by `plan_id`.
- **Member sync**: Insert all current joined `plan_members.user_id` into `conversation_members` with `ON CONFLICT DO NOTHING`.
- **Return**: `conversation_id uuid`.

### B. New RPC or trigger: sync `conversation_members` with `plan_members`
- **Option 1 (Trigger)**: `AFTER UPDATE` on `plan_members` when `status` changes to/from `joined`:
  - `joined` → insert into `conversation_members`.
  - `left`/`removed`/`declined` → delete from `conversation_members`.
- **Option 2 (RPC)**: Expose `sync_plan_conversation_members(p_plan_id)` called from the client after approve/decline/remove. Less real-time but simpler to reason about.
- **Recommendation**: Trigger-based sync is more robust; use a SECURITY DEFINER trigger that queries `plan_members` and reconciles `conversation_members`.

### C. `ChatRepository` — Add plan-chat methods
- `Future<ChatResult<String>> getOrCreatePlanConversation(String planId)`
- `Future<ChatResult<List<ChatConversation>>> loadPlanConversations()` — queries `conversations` where `plan_id IN (…)` and caller is a member.
- `Future<ChatResult<GroupMetadata?>> loadGroupMetadata(String conversationId)` — projects plan title + participants from `plan_members` and `profiles`.

### D. `RealtimeMessagesService` — Group/plan chat realtime
- `ConversationScreen.initState()` should call `_startRealtime()` for both `ConversationType.private` and `ConversationType.group`.
- `RealtimeMessagesService` itself is already generic (per-conversation channel + global channel), so no service change is needed. Only the guard in `ConversationScreen` must be relaxed.

## 23. Required migration

**YES**

### Exact reason
A new migration is required to add:
1. `get_or_create_plan_conversation(p_plan_id uuid)` SECURITY DEFINER RPC.
2. (Recommended) A trigger function + trigger on `plan_members` to auto-sync `conversation_members` when a member transitions to/from `joined`.
3. (Alternative to trigger) RPC `sync_plan_conversation_members(p_plan_id)` if trigger approach is rejected.
4. A unique constraint on `conversations(plan_id)` where `plan_id IS NOT NULL` to guarantee one conversation per plan (or handle in RPC logic).

### Minimal migration SQL sketch (for planning)
```sql
-- 1. Unique constraint: one plan conversation per plan
CREATE UNIQUE INDEX IF NOT EXISTS idx_conversations_plan_id_unique
  ON public.conversations(plan_id)
  WHERE plan_id IS NOT NULL;

-- 2. RPC: get_or_create_plan_conversation
CREATE OR REPLACE FUNCTION public.get_or_create_plan_conversation(
  p_plan_id uuid
)
RETURNS uuid
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public
AS $$
DECLARE
  v_conversation_id uuid;
  v_current_user uuid := auth.uid();
  v_is_creator boolean;
  v_is_member boolean;
BEGIN
  IF v_current_user IS NULL THEN
    RAISE EXCEPTION 'Not authenticated';
  END IF;

  SELECT creator_id = v_current_user INTO v_is_creator
  FROM public.plans WHERE id = p_plan_id;

  SELECT EXISTS (
    SELECT 1 FROM public.plan_members
    WHERE plan_id = p_plan_id AND user_id = v_current_user AND status = 'joined'
  ) INTO v_is_member;

  IF NOT v_is_creator AND NOT v_is_member THEN
    RAISE EXCEPTION 'Not a participant of this plan';
  END IF;

  SELECT id INTO v_conversation_id
  FROM public.conversations
  WHERE plan_id = p_plan_id AND type = 'plan'
  LIMIT 1;

  IF v_conversation_id IS NULL THEN
    INSERT INTO public.conversations (type, plan_id)
    VALUES ('plan', p_plan_id)
    RETURNING id INTO v_conversation_id;
  END IF;

  INSERT INTO public.conversation_members (conversation_id, user_id)
  SELECT v_conversation_id, pm.user_id
  FROM public.plan_members pm
  WHERE pm.plan_id = p_plan_id AND pm.status = 'joined'
  ON CONFLICT (conversation_id, user_id) DO NOTHING;

  RETURN v_conversation_id;
END;
$$;

GRANT EXECUTE ON FUNCTION public.get_or_create_plan_conversation(uuid) TO authenticated;

-- 3. Trigger: sync conversation_members on plan_members status change
CREATE OR REPLACE FUNCTION public.sync_plan_conversation_members()
RETURNS TRIGGER
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public
AS $$
DECLARE
  v_conversation_id uuid;
BEGIN
  IF TG_OP = 'UPDATE' AND NEW.status = OLD.status THEN
    RETURN NEW;
  END IF;

  SELECT id INTO v_conversation_id
  FROM public.conversations
  WHERE plan_id = NEW.plan_id AND type = 'plan'
  LIMIT 1;

  IF v_conversation_id IS NULL THEN
    RETURN NEW;
  END IF;

  IF NEW.status = 'joined' THEN
    INSERT INTO public.conversation_members (conversation_id, user_id)
    VALUES (v_conversation_id, NEW.user_id)
    ON CONFLICT (conversation_id, user_id) DO NOTHING;
  ELSE
    DELETE FROM public.conversation_members
    WHERE conversation_id = v_conversation_id AND user_id = NEW.user_id;
  END IF;

  RETURN NEW;
END;
$$;

DROP TRIGGER IF EXISTS trg_sync_plan_conversation_members ON public.plan_members;
CREATE TRIGGER trg_sync_plan_conversation_members
  AFTER UPDATE OF status ON public.plan_members
  FOR EACH ROW
  EXECUTE FUNCTION public.sync_plan_conversation_members();
```

## 24. Potential architecture conflicts

### A. Conversation ID scheme mismatch
- Connection conversations use deterministic `md5(connectionId)` IDs.
- Plan conversations currently have no ID scheme. The RPC above generates a fresh UUID on creation, which is fine because there is exactly one conversation per plan. If deterministic IDs are desired for caching, use `md5(planId || '-conexo-plan-v1')::uuid`, but this is not required.

### B. Realtime inbox mapping
- `ConnectionsInboxScreen._conversationToConnectionMap` maps conversation IDs to connection IDs for realtime unread updates (`connections_screen.dart:61`, `121-123`).
- Plan conversations have no equivalent map. The Plans tab realtime updates would need a separate map (e.g., `_conversationToPlanMap`) or a unified map keyed by conversation ID with a type discriminator.

### C. `conversation_screen.dart` send guard
- `_sendMessage` (`conversation_screen.dart:214-216`) returns early if `widget.chatRepository == null`. Plan chat entries pushed without a repository would silently fail to send. All plan chat routes must pass `ChatRepository`.

### D. RLS recursion risk
- New RPCs or triggers that join `plan_members` → `plans` → `plan_members` could hit infinite RLS recursion. The existing `is_plan_creator` / `is_plan_member` SECURITY DEFINER helpers (`20260829020000_fix_plan_rls_recursion.sql`) should be reused or the new logic must run with `SECURITY DEFINER` and explicit `search_path`.

### E. `plan_id` not set by existing code
- Any new query filtering `conversations` by `plan_id` must handle `NULL` rows (connection conversations). The partial unique index `WHERE plan_id IS NOT NULL` mitigates this.

## 25. Existing functionality that MUST NOT change

1. **Connection 1:1 chat** — `getOrCreateConnectionConversation`, realtime, inbox, message send/load must remain identical.
2. **Plan membership lifecycle** — `requestToJoin`, `approvePlanMember`, `declinePlanMember`, `removePlanMember`, capacity enforcement, and all RLS policies on `plan_members` must remain untouched.
3. **Plan discovery / visibility** — `getDiscoveryPlans`, `getJoinedExperiences`, `getRequestedExperiences` must continue to hide/request plans correctly.
4. **Notification navigation for messages** — `NotificationKind.message` → connection conversation must continue to work.
5. **Conversation screen private path** — drafts, block/report, message rendering for `ConversationType.private` must not regress.
6. **Storage / cover upload** — `plan-covers` bucket policies and `savePublished` cover flow must remain unchanged.
